# Панель и рабочие столы

Разбор одного бага, на который заходили трижды: **панель не открывается по
щелчку — то не появляется вовсе, то мелькает и гаснет, то обнаруживается на
соседнем столе**. Два первых захода чинили симптом и делали хуже, потому что
опирались на признаки, которые в этом месте врут.

Документ нужен, чтобы третий раз не начинать с нуля: здесь измеренные данные,
готовые пробы и правило, по которому проверяется любая правка `DropdownPanel`.

Смежное: [ARCHITECTURE.md](ARCHITECTURE.md) — карта кода и раздел «Грабли».

---

## 1. Как это выглядит со стороны

Жалобы звучат по-разному, а причина одна:

- «в IDE не открывается, а на другом столе открылась»;
- «открывает через окно» — панель находится через один рабочий стол;
- «щёлкаю — ничего, щёлкаю второй раз — появилась»;
- «уехала на полноэкранное, где видео».

Общий признак: **щелчок по значку не даёт панели там, где человек сейчас.**
Позиция при этом всегда считалась правильно — это проверено (§4), и искать
надо не в `frame(for:anchor:)`.

## 2. Как устроено сейчас

Панель (`DropdownPanel`, окно `MenuPanel`) живёт **на одном рабочем столе** и
переезжает на текущий, когда её показывают:

```swift
collectionBehavior = [.moveToActiveSpace, .fullScreenAuxiliary, .stationary, .ignoresCycle]
```

Отсюда три следствия, на которых держится всё поведение:

| Что | Как |
|---|---|
| «Панель показана здесь?» | `isShown` = `isVisible && panel.isOnActiveSpace` — спрашиваем у окна, и ответ честный |
| Уход на другой стол | панель уезжает вместе с покинутым столом; `handleSpaceChange` закрывает её, когда `!panel.isOnActiveSpace` |
| Показ | `orderOut` перед каждым `orderFrontRegardless` — снятое с экрана окно достаётся текущему столу, оставшееся висеть держится за прежний |

Переезд делает именно показ, а не объявление флага: пока окно висит, оно
остаётся на своём столе. Поэтому `orderOut` в `show(from:)` — не
перестраховка, а механизм переезда.

## 3. Почему два прежних решения не работали

Оба захода пытались вычислить, на своём ли столе панель. Ни один из двух
доступных признаков на этот вопрос не отвечает.

**Признак первый — `isOnActiveSpace` у окна с `.canJoinAllSpaces`.** Такое окно
присутствует на всех столах разом, поэтому свойство отвечает «да» всегда, пока
окно видимо. Проверки, построенные на нём, были мёртвыми.

**Признак второй — список окон на экране.** Ему на замену взяли
`CGWindowListCopyWindowInfo` с `.optionOnScreenOnly`: нет `panel.windowNumber`
в списке — значит, панель на чужом столе. Список обновляется с задержкой и
окна, показанного только что, не содержит. В прогоне он отвечал «нет» даже в
строке, напечатанной сразу после `orderFrontRegardless`, и через секунду после
неё. Последствий два, и оба — ровно те жалобы из §1:

- `handleSpaceChange` считал только что открытую панель чужой и **закрывал
  её** — панель гасла сама через секунду после появления;
- `togglePanel` видел `isShown == false` при открытой панели, поэтому щелчок
  по значку **не закрывал** её, а показывал заново.

Вывод, который стоит помнить: **вопрос «на каком я столе» окну с
`.canJoinAllSpaces` задавать бесполезно, а списку окон — бесполезно вдвойне.**
Либо окно живёт на одном столе и отвечает само, либо ответа нет.

## 4. Что измерено

Данные с macOS 26.5, один экран 1470×956, три-четыре стола плюс полноэкранные.

**Позиция панели всегда верна.** Лог из приложения в момент щелчка:

```
показ: значок=(1082.0, 923.0, 34.0, 33.0) экранЗначка=(0.0, 0.0, 1470.0, 956.0)
       размер=(380.0, 166.0) целевая=(909.0, 757.0, 380.0, 166.0)
показана: рамка=(909.0, 757.0, 380.0, 166.0) видима=true наЭкране=false
```

Панель встала под значок, вплотную к строке меню. `наЭкране=false` в той же
строке — это и есть врущий список окон.

**Панель гасла сама.** Пары строк «показ → закрытие» без щелчка между ними,
семь штук за прогон:

```
18:21:10 показ ... былаОткрыта=false наЭкране=false
18:21:10 показана: ... видима=true наЭкране=false
18:21:11 смена стола: открыта=true наЭкране=false
18:21:11 закрытие (смена стола): открыта=true
```

**Щелчок не закрывал панель.** `панельПоказана=false` при открытой панели:

```
18:21:13 клик по значку: панельПоказана=false → показ (былаОткрыта=false)
18:21:14 клик по значку: панельПоказана=false → показ (былаОткрыта=true)
```

**`.moveToActiveSpace` отвечает честно, `.canJoinAllSpaces` — нет.** Проба
`--behaviors`, столы переключались вручную:

```
активный стол:4 | M: на своём столе=НЕТ столы=173 | C: на своём столе=да столы=173,192,3,4
активный стол:4 | M: на своём столе=да  столы=4   | C: на своём столе=да столы=173,192,3,4
```

Первая строка — сразу после ухода на стол 4, вторая — после показа заново:
окно M переехало (`столы=4`), окно C по-прежнему висит на всех столах и
уверяет, что оно «на своём». Между строками — переоткрытие окна, то есть
переезд делает показ.

**Полноэкранные столы не особенные.** Окно с `.moveToActiveSpace` переезжало и
в них (в логах это столы с номерами вроде 95, 132, 146, 154 — они заводятся и
исчезают вместе с полноэкранным окном).

## 5. Как разбирать это заново

Обе пробы лежат в репозитории — [scripts/probe-panel.swift](../scripts/probe-panel.swift).

**Шаг 1. Панель гаснет сама или это щелчок?** Отвечает на главный вопрос, не
трогая приложение:

```
swift scripts/probe-panel.swift --watch
```

Щёлкайте по значку и ходите по столам. В логе будут щелчки и каждое появление
и пропадание панели с координатами и номерами столов. `пропала` без `клик`
перед ней — панель закрыл кто-то в коде: ищите вызовы `close()`
(`handleSpaceChange`, мониторы щелчков, `hideWhilePinned`).

**Шаг 2. Что видит само приложение.** Если наблюдения снаружи мало, временно
добавьте в `DropdownPanel` вывод в `show(from:)`, `close()` и
`handleSpaceChange` — рамку значка, посчитанную рамку панели, `isShown` и
`panel.isOnActiveSpace`, — и запустите отладочную сборку вместо установленной:

```
launchctl stop com.greem4.claudeweek && pkill -f "Applications/ClaudeWeek.app"
swift build && ./.build/debug/ClaudeWeekApp        # логи идут в stderr
./scripts/install.sh                               # вернуть рабочую версию
```

Так и был найден `наЭкране=false` из §4: снаружи этого не видно.

**Шаг 3. Проверка флагов окна.** Прежде чем менять `collectionBehavior`:

```
swift scripts/probe-panel.swift --behaviors
```

Чтением документации это не решается: поведение зависит от версии macOS и от
того, полноэкранный стол или обычный. Проба даёт ответ за минуту.

## 6. Чего не делать

- **Не возвращать `.canJoinAllSpaces`** без замены механизма целиком: с ним
  панель висит на всех столах, едет вместе со свайпом и гаснет уже на новом
  столе — то самое мигание, — а `isOnActiveSpace` перестаёт отвечать.
- **Не строить «панель здесь?» на списке окон** (`CGWindowListCopyWindowInfo`):
  он отстаёт, см. §3.
- **Не лечить таймингом.** Порог «показ моложе секунды не закрываем» проверку
  чинит на вид, но остаётся догадкой о скорости системы; честный признак у
  окна на одном столе делает его ненужным.
- **Не путать `isShown` и `isOpen`.** `isShown` — «человек видит панель здесь»
  (щелчок по значку, `resize`); `isOpen` — «есть ли что закрывать» (`close`,
  мониторы щелчков, `pinToAnchor`), он же `isVisible`.
- **Не проверять правку на одном столе.** Минимальный прогон: открыть панель и
  уйти свайпом; вернуться и щёлкнуть; щёлкнуть сразу после свайпа, не дожидаясь
  конца анимации; повторить в полноэкранном окне чужого приложения.

## 7. Два монитора: панель у чужого края

Отдельная жалоба с той же внешностью — «панель вылезла за экран», — но причина
другая, и столы к ней отношения не имеют.

**Что видно.** Два монитора один над другим, на нижнем открыто полноэкранное
окно (VS Code, zen mode). Щелчок по значку — и панель появляется не под строкой
меню, а внизу *верхнего* монитора, оторванная от неё на пол-экрана.

**Почему.** Строка меню в полноэкранном режиме прячется, и WindowServer уводит
её окно вместе со значками вверх ровно на свою высоту — за верхнюю кромку
своего экрана. Замер на машине с двумя DELL 1920×1080 (нижний экран
`y 0…1080`, верхний `y 1080…2160`):

```
layer 24 Window Server x0 w1920 h30  AppKit y 1050…1080  экран 1  ← строка меню видна
layer 24 Window Server x0 w1920 h30  AppKit y 1080…1110  экран 2  ← она же спрятана
```

Спрятанная строка меню нижнего экрана лежит на территории верхнего: мониторы
стоят вплотную, и 30 точек сдвига переносят её через границу. `anchor.screen`
отвечает «экран 2» — честно и бесполезно. Дальше срабатывал клэмп
`origin.y = max(origin.y, screen.minY + margin)`, и панель прижималась к нижней
кромке верхнего монитора. Расчёт совпал с измеренным положением до точки:

```
значок y1080…1110 → было: экран 2, панель y1088…1416   (1088 = 1080 + 8)
                    стало: экран 1, панель y752…1080
```

**Чем чинится.** `DropdownPanel.screen(for:)` выбирает экран не по
`anchor.screen`, а по признаку, который сдвиг переживает: строка меню всегда
прижата к верхней кромке своего экрана, значит значок принадлежит тому из
накрывающих его по горизонтали экранов, чья верхняя кромка к нему ближе.
Плюс верхняя кромка панели ограничена сверху `screen.maxY`: спрятанная строка
меню уводила бы за край и её.

**Чего не делать.** Не подставлять `NSScreen.main` — это экран с клавиатурным
фокусом, то есть чужого активного окна, а не нашего значка. Не искать экран
пересечением с рамкой значка: у спрятанной строки меню оно приводит к соседу.

**Как проверить.** `swift scripts/probe-panel.swift --displays` — печатает, где
лежит окно значка и что про него думает каждый монитор. Прогон: щёлкнуть по
значку на каждом мониторе; открыть на нижнем полноэкранное окно и щёлкнуть
снова; повторить с полноэкранным на верхнем.
