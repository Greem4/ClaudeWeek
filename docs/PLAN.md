# ClaudeWeek — план реализации

Меню-бар приложение для macOS, показывающее расход недельного лимита Claude Code:
на каждой полосе два цвета — **план** (сколько допустимо потратить к этому моменту)
и **факт** (сколько реально потрачено).

Документ — рабочий план: что делаем, почему именно так, в каком порядке и как
проверяем. Все технические допущения из раздела «Проверенное окружение» проверены
на этой машине, а не взяты из документации.

**Состояние на 2026‑08‑05.** Сделаны все этапы, M0—M6. Приложение собирается,
стоит под LaunchAgent и показывает официальный процент из `/api/oauth/usage`
(схема — [`docs/API.md`](API.md)); локальный расчёт по транскриптам остался
запасным источником и включается сам, когда официальный недоступен. Момент
сброса недели берётся из ответа сервера, а не из конфига.

Сверх плана появились: строка пятичасовой сессии, окно настроек с темами и
прозрачностью. Свой токен тоже был, но вырезан: эндпоинт принимает только
токен сеанса Claude Code — разбор в [API.md](API.md#токен). Этот файл — план и
обоснования решений, он застыл на момент написания; **актуальная справка —
[README](../README.md) и [ARCHITECTURE.md](ARCHITECTURE.md)**, а чего ещё нет —
[ROADMAP.md](ROADMAP.md).

## 1. Что получится в итоге

Два уровня детализации — беглый взгляд и разбор.

**В строке меню** — компактный индикатор. Видно, не открывая ничего:

```
▍▍▍▍░░
  64%
```

Число — фактически потраченный процент недельного лимита. Полоса и число —
одна иконка в два этажа, чтобы пункт занимал поменьше ширины. Цвет числа и
полоски меняется по состоянию: в графике / обгоняю план / лимит на исходе.

**По клику — панель** со всей неделей, по мотивам исходного скриншота,
но с добавленным вторым цветом:

```
┌──────────────────────────────────────────────────────────┐
│  ЛИМИТ НЕДЕЛИ    сброс ПТ 15:00        ≈14 % в сутки     │
│  ────────────────────────────────────────────────────────│
│  ПТ  ███████░░░░░░░░░░░░░░                  7 / 7 %      │
│  СБ  ██████████████▒▒▒▒▒▒░                 15 / 21 %     │
│  ВС  ████████████████████▒▒▒▒▒▒▒▒░         28 / 36 %     │
│  ПН  ██████████████████████████████▓▓▓░    58 / 50 %     │
│  ВТ  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░      — / 64 %     │
│  ────────────────────────────────────────────────────────│
│  осталось 42 % · до сброса 3 дн 6 ч · темп 1.4× плана    │
└──────────────────────────────────────────────────────────┘
```

- `█` — факт в пределах плана (зелёный),
- `▓` — часть факта, вышедшая за план (янтарный),
- `▒` — остаток плана, ещё не потраченный (приглушённый синий),
- `░` — за пределами плана этого дня (нейтральный серый трек).

Читается за секунду: где зелёное упирается в синее — идём вровень; где синее
торчит справа — есть запас; где появился янтарный — перерасход.

## 2. Модель данных: неделя, план, факт

### 2.1 Недельное окно

Лимит сбрасывается раз в 7 суток в фиксированный момент. Источник правды —
официальный ответ: `seven_day.resets_at` даёт конец окна, начало отсчитывается
на 7 суток назад. Конфиг (`resetWeekday`, `resetHour`, `resetMinute`) — запасной
путь для офлайна и локального источника; окно считается в локальной таймзоне
(на этой машине — `Europe/Saratov`, UTC+4).

```
end   = resets_at из ответа        (офлайн: последний прошедший «ПТ 15:00»)
start = end − 7 суток              (через Calendar, не через −604800 секунд)
progress(t) = (t − start) / (end − start)        ∈ [0, 1]
```

Почему сервер, а не конфиг: на этой машине конфиг говорил «пятница 15:00», а
реальный сброс оказался в 16:00 по Саратову (`12:00Z`) — час разницы взялся из
того, что число подсматривали по московскому времени. Догадка пользователя
сдвигает все семь полос; ответ сервера — нет.

Прибавление делаем календарно (`Calendar.date(byAdding: .day, value: 7, ...)`),
а не арифметикой по секундам: при переходе на летнее время сутки бывают 23 или
25 часов, и «сброс в 15:00» должен остаться в 15:00.

### 2.2 План — что означают числа на скриншоте

Разбор исходных цифр: 7, 21, 36, 50, 64, 79, 93, 100. Это ровно

```
plan(d) = (d + 0.5) / 7,   d = 0…6   →  7.1, 21.4, 35.7, 50.0, 64.3, 78.6, 92.9 %
```

то есть **значение плана на середину каждых суток**, плюс финальные 100 % на
момент сброса. При этом подпись на скриншоте гласит «сколько можно потратить
**к концу дня**» — а «к концу дня» дало бы 14, 29, 43, 57, 71, 86, 100 %.

Расхождение подписи и цифр — не наша выдумка, а факт исходника; решение по нему
принято в §10 (берём вариант, подтверждённый цифрами). Реализована **непрерывная
модель**, которая покрывает оба прочтения:

```
planAt(t) = progress(t)                       // непрерывный план на момент t
```

а строка дня показывает **накопительный план к концу этих суток** — как
в подписи исходника. Выбора опорной точки (`planAnchor`: `midDay` / `endOfDay`)
больше нет: факт в строке накопительный и берётся на конец тех же суток, и
сравнивать его с планом на середину значило бы всю неделю показывать
перерасход там, где его нет.

**`progress(t)` считается по рабочим часам, а не по астрономическим** — это
появилось позже плана и переписало формулу целиком (`WorkHours`,
`WeekWindow.progress`). Линейная шкала давала вечеру пятницы после сброса
(8 часов, все рабочие) вдвое меньше плана, чем её утру (16 часов, из которых
рабочих 5), — сон весил столько же, сколько работа. Теперь 100 % делятся на
рабочие секунды окна: при дне 11:00 → 00:00 и сбросе в 16:00 в неделе 91
рабочий час, ночью план стоит. Круглосуточный режим (`workHours: 0…24`)
возвращает прежнюю линейную шкалу.

Заголовок «≈14 % в сутки» — это `100 / 7 = 14.3 %`, равномерный темп; в панели
его больше нет (полные сутки и так весят одинаково, а неполные — нет).

### 2.3 Факт

Источник — официальный процент из аккаунта (§3). Раскладка по дням: факт дня —
это накопительный расход от начала недели до конца этих суток, чтобы обе
величины на полосе были в одной шкале (накопительной). Дни в будущем факта не
имеют — рисуется только план.

**Откуда берётся раскладка при официальном источнике.** Официальный ответ даёт
одно число — процент на текущий момент, без разбивки по суткам. Решение
(подтверждено владельцем): форму недели берём из локальных транскриптов и
масштабируем к официальному итогу — доля каждых суток в локальной стоимости
умножается на официальный процент. Итог тогда точный, а форма правдоподобная;
панель заполнена с первого запуска. Отвергнутые варианты: копить историю
собственных замеров (первая неделя пустая, пропуски при выключенном Mac) и
показывать только общий итог без суточных полос (панель теряет смысл).

### 2.4 Производные величины для футера

- `remaining = 100 − факт` — сколько осталось;
- `timeLeft = end − now` — до сброса;
- `burnRate = факт / planAt(now)` — темп: 1.0 = ровно по плану, 1.4 = тратим в
  полтора раза быстрее, чем можно;
- `projected = факт / progress(now)` — прогноз расхода к моменту сброса при
  сохранении текущего темпа; если > 100 %, показываем дату/время, когда лимит
  закончится. С рабочими часами делением этот момент больше не находится:
  его ищет `WeekWindow.date(atProgress:)`, обратная к `progress`, — иначе
  прогноз обещал бы исчерпание в четыре утра, когда никто не работает.

## 3. Источник данных

Решение: **официальный процент из аккаунта**, с локальным расчётом как запасным
источником, если официальный недоступен.

### 3.1 Официальный источник (основной)

Тот же процент, что показывает `/usage` внутри Claude Code. Локально он нигде не
лежит: проверено — `~/.claude/stats-cache.json` содержит только `dailyActivity`
и `dailyModelTokens` (сообщения, сессии, вызовы инструментов, токены по моделям),
никаких полей лимита; в 193 файлах транскриптов полей вида `rate_limit` /
`resets_at` тоже нет. Значит, за числом нужно идти в сеть.

**Сделано.** Схема, дисциплина запросов и способ перепроверки — в
[`docs/API.md`](API.md). Ниже — что выяснилось против ожиданий.

**М2.1. Разведка эндпоинта. Сделано.** Живой сессии `claude --debug api` не
потребовалось: путь и форма ответа нашлись строками в бинаре клиента (функция
`fetchUtilization`), а живой ответ снят одним запросом —
`scripts/probe-usage.swift`. Итог:
`GET https://api.anthropic.com/api/oauth/usage`, авторизация голым `Bearer`,
beta-заголовки не нужны (проверены три варианта). Недельный процент —
`seven_day.utilization`, момент сброса — `seven_day.resets_at`.

**М2.2. Токен. Сделано.** Запись Keychain действительно называется
`Claude Code-credentials`; токен лежит в `claudeAiOauth.accessToken`, живёт
около часа, `expiresAt` — в миллисекундах. Читаем через Security.framework,
запись перечитываем перед каждым запросом.

Следствия подтвердились:

- при первом обращении macOS показывает системный диалог доступа — это
  ожидаемое поведение, а не ошибка;
- разрешение привязано к подписи бинаря, и при ad-hoc подписи диалог всплывает
  после каждой пересборки. На время разработки — «Всегда разрешать»;
  долгосрочно — стабильная подпись (Developer ID).

Отдельное решение: **своего refresh-цикла у ClaudeWeek нет.** Обновлять токен
умеет Claude Code, и два процесса, наперегонки переписывающие одну запись
Keychain, теряют его. На `401` мы уходим на локальную оценку и через минуту
перечитываем запись — к этому моменту Claude Code обычно уже обновил токен.

**М2.3. Дисциплина запросов. Сделано.**

- опрос не чаще одного раза в 60 секунд, независимо от `refreshInterval`;
- ответ кладём в `~/.config/claude-week/cache.json` (с `fetchedAt`), при старте
  показываем кеш мгновенно, потом обновляем; кеш прошлой недели отбрасываем;
- 401/403 → локальная оценка; 429/5xx и отказ сети → пауза
  1 → 2 → 4 → 8 → 15 минут;
- никаких запросов, пока Mac спит: таймер гасится на `willSleepNotification`.

Отличие от первоначального плана: на 401 опрос **не** прекращается до
перезапуска. Причина та же — токен обновляет Claude Code, и перезапуск виджета
ради этого лишний.

**М2.4. Приватность. Сделано.** Токен не логируется, не пишется на диск и не
выводится в UI; единственный сетевой адресат — `api.anthropic.com`; в кеш идут
только проценты, границы окна и метка времени.

### 3.2 Локальный расчёт (fallback)

Работает офлайн, включается, когда официальный источник недоступен; в UI
помечается «≈ оценка» (и цветом, и подписью, чтобы приблизительность не выдавалась
за точное число).

**Данные.** `~/.claude/projects/**/*.jsonl` — по строке на событие. У ассистентских
сообщений есть `message.usage` с `input_tokens`, `output_tokens`,
`cache_creation_input_tokens`, `cache_read_input_tokens`, а также `message.model`
и `timestamp`. Проверено на этой машине: 193 файла, 13 508 сообщений с `usage`.
Замер после реализации: холодный проход — 1.3 с, повторный по индексу — 0.04 с.

**Взвешивание.** Токены разных типов и моделей стоят по-разному, поэтому суммируем
не «штуки», а стоимость (цены за 1 Mtok, на 2026‑08‑04):

| Модель | вход | выход | запись кеша (5 м) | чтение кеша |
|---|---|---|---|---|
| Opus 5 (`claude-opus-5`) | $5 | $25 | ×1.25 от входа | ×0.1 от входа |
| Sonnet 5 (`claude-sonnet-5`) | $3 | $15 | ×1.25 | ×0.1 |
| Haiku 4.5 (`claude-haiku-4-5`) | $1 | $5 | ×1.25 | ×0.1 |

Для 1‑часового кеша множитель записи ×2. Неизвестная модель → веса Sonnet,
запись в лог. Итог — «условная стоимость недели», которая делится на
калиброванный бюджет (`weeklyBudget` в конфиге).

**Калибровка.** Бюджет подбирается сам: на каждом успешном официальном ответе
локальная стоимость недели делится на официальный процент, и результат ложится
в `cache.json` (не в `config.json` — самовольно править пользовательский конфиг
приложение не должно). Когда сеть пропадает, офлайн-оценка берёт этот бюджет и
последний известный момент сброса, сдвинутый на нужное число недель. Замер на
реальных данных: 52 % официальных против 52 % офлайн-оценки.

Ручной путь остался для случая, когда официального ответа не было ни разу:
увидели в `/usage` 64 % — `--calibrate=64` записывает в конфиг
`calibration: { observedPercent: 64, at: "…" }` и `weeklyBudget`. Заданный
человеком бюджет всегда важнее подобранного.

**Производительность.** Инкрементальное чтение: в `~/.config/claude-week/index.json`
храним по файлу `(path, inode, size, offset, mtime)` и читаем только хвост.
Смена inode или уменьшение size → файл перечитывается целиком. Дедупликация — по
`uuid` сообщения, чтобы записи, попавшие и в основной транскрипт, и в
`subagents/*.jsonl`, не считались дважды.

### 4.2 Ключевые типы

```swift
protocol UsageProvider {
    var kind: SourceKind { get }              // .official / .local
    func fetch() async throws -> UsageSnapshot
}

struct UsageSnapshot {
    let usedPercent: Double                   // факт, 0…100+
    let byDay: [DayUsage]                     // накопительный факт по суткам
    let window: WeekWindow
    let source: SourceKind
    let fetchedAt: Date
    let isEstimate: Bool                      // true для локального источника
    let shapeIsEstimate: Bool                 // форма недели восстановлена
    let session: SessionUsage?                // пятичасовой лимит, если известен
}

struct SessionUsage {
    let usedPercent: Double                   // расход сессии, 0…100
    let resetsAt: Date                        // после него процент обнуляется
}
```

`ResolvingProvider` дёргает официальный провайдер, при неудаче — локальный, и
пишет кеш. UI знает только про `UsageSnapshot`, ему всё равно, откуда цифры.

Двух флагов приблизительности не избежать: у официального источника итог точный
(`isEstimate = false`), а разбивка по суткам всё равно восстановлена по
транскриптам (`shapeIsEstimate = true`). Одним флагом это не выразить, а
умолчать — значит выдать приблизительные полосы за официальные.

### 4.3 Сборка без Xcode

Проверено на этой машине: Xcode не установлен (только Command Line Tools), но
SwiftUI и AppKit есть в SDK CLT, и тестовый файл с `NSStatusItem` + SwiftUI
компилируется `swiftc` без ошибок. Значит, меню-бар приложение собирается так:

```bash
# scripts/make-app.sh делает всё сам:
swift build -c release --product ClaudeWeekApp
#   ClaudeWeek.app/Contents/MacOS/ClaudeWeek           ← бинарь
#   ClaudeWeek.app/Contents/Info.plist
#   ClaudeWeek.app/Contents/Resources/ClaudeWeek.icns  ← иконка, --icon + iconutil
codesign --force --sign - ClaudeWeek.app     # ad-hoc подпись
```

Иконка рисуется кодом (`AppIcon.swift` → `.iconset` → `iconutil`): без Xcode
собрать ассет-каталог нечем, а `iconutil` есть в Command Line Tools.

`Info.plist` — минимальный, но с обязательным `LSUIElement = true`: приложение не
должно появляться в Dock и в переключателе программ.

| Ключ | Значение |
|---|---|
| `CFBundleIdentifier` | `com.greem4.claudeweek` |
| `CFBundleExecutable` | `ClaudeWeek` |
| `LSUIElement` | `true` |
| `LSMinimumSystemVersion` | `14.0` |
| `CFBundleIconFile` | `ClaudeWeek` |
| `NSHumanReadableCopyright` | — |

### 4.4 Автозапуск

`scripts/install.sh` кладёт
`~/Library/LaunchAgents/com.greem4.claudeweek.plist` c `RunAtLoad = true` и
`KeepAlive = false`, затем `launchctl bootstrap gui/$UID …`. Повторный запуск —
полная переустановка: сборка свежего бандла, затем снос прежнего (все агенты,
чьи plist поминают ClaudeWeek, работающий процесс, приложение в `~/Applications`
и `/Applications`) и только потом установка новой версии. Копии не плодятся.
Удаление — `uninstall.sh`, он сносит ровно то же самое.

Тот же агент правит галочка «Запускать при входе в систему» на вкладке
«Общие» (`LoginItem.swift`): label, путь плиста и файл лога совпадают до буквы, а
`bootstrap`/`bootout` она не зовёт — файла довольно, чтобы launchd поднял
приложение со следующего входа.

## 5. Дизайн

### 5.1 Анатомия полосы

Полоса — это bullet-график: фон-трек (весь недельный лимит), зона плана и поверх
неё фактическая заливка.

```
│◀──────────────── 100 % недельного лимита ────────────────▶│
│█████████████████████│▒▒▒▒▒▒▒▒▒▒│░░░░░░░░░░░░░░░░░░░░░░░░░░│
 ←─── факт 34 % ────→ ←─ план ─→
                       остаток
                                  ↑ 52 % — плановая отметка дня
```

Перерасход — тот же трек, но кусок факта за плановой отметкой красится янтарным
и отделяется от зелёного зазором в 2 px цвета фона:

```
│███████████████████████████│▓▓▓▓▓▓│░░░░░░░░░░░░░░░░░░░░░░░│
 ←────── план 52 % ──────→ ↑ ←вылет→
                            2 px зазор
```

Зазор — не украшение: это вторичный канал кодирования, который держит границу
читаемой, когда цвета сливаются (дальтонизм, ч/б печать, скриншот в мессенджере).

Спецификация марок:
- высота полосы 9 pt, скруглённые концы (`Capsule`);
- ширина трека — на всю доступную ширину строки, дни выровнены по левому краю;
- анимация заполнения 0.35 с, `easeOut`; при обновлении цифр — только полоса,
  без «прыжка» чисел (моноширинные цифры, `tabular-nums`).

**Полоса сессии устроена проще:** трек и одна заливка, без зоны плана.

```
│◀────────────── 100 % пятичасового лимита ────────────────▶│
│█████████████████████████│░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
 ←──── факт 41 % ──────→
```

Плановой зоны здесь нет намеренно: пятичасовое окно не обязано расходоваться
равномерно — работу можно просто закончить, — и синяя отметка «сколько положено
к этому часу» изображала бы темп, которого у сессии по смыслу нет. Заливка
зелёная, за порогом `thresholds.critical` — янтарная; при 100 % добавляются
значок `⚠` и красные цифры, потому что цвет заливки один смысл нести не может.
Метка и колонка значения шириной как у суток: строка стоит над разделителем,
в общей сетке, но по свою его сторону.

### 5.2 Палитра

Цвета не подобраны на глаз — прогнаны через валидатор палитры (проверка
разделимости при дальтонизме, контраста к фону и насыщенности) в обеих темах.

| Роль | Светлая | Тёмная | Комментарий |
|---|---|---|---|
| Трек (вне плана) | `#e1e0d9` | `#2c2c2a` | нейтраль на шаг от фона |
| **План** (остаток) | `#6da7ec` | `#3987e5` | приглушённый синий, фон под факт |
| **Факт** (в пределах плана) | `#0ca30c` | `#0ca30c` | статус «good» |
| **Вылет за план** | `#fab219` | `#fab219` | статус «warning» |
| Критично (≥100 % / прогноз исчерпания) | `#d03b3b` | `#d03b3b` | только в заголовке и иконке |
| Фон панели | `#fcfcfb` | `#1a1a19` | только `--screenshot`; живьём — `NSVisualEffectView` |
| Основной текст | чёрный 85 % | белый 85 % | плотность системного `labelColor` |
| Вторичный текст | чёрный 62 % | белый 55 % | подписи дней, футер; 6.0:1 и 5.9:1 к фону |

Результаты проверки и что с ними делаем:

- **Разделимость цветов проходит в обеих темах**: худшая пара «факт ↔ вылет» даёт
  ΔE 11.3 при протанопии и 27.6 при нормальном зрении (пороги 8 и 15).
- **Тританопия в тёмной теме** даёт по этой паре ΔE 5.1 — ниже порога, поэтому
  вторичное кодирование обязательно: 2 px зазор между сегментами, число
  `факт / план` в каждой строке и значок ⚠ у строк с перерасходом. Цвет нигде не
  остаётся единственным носителем смысла.
- **Контраст к светлому фону** у плана (2.44:1) и янтарного (1.79:1) ниже 3:1 —
  это допустимо для заливок при наличии видимых подписей, которые у нас есть в
  каждой строке. Текстом эти цвета не красим никогда.
- Красный `#d03b3b` и зелёный `#0ca30c` неразличимы при дейтеранопии (ΔE 4.1),
  поэтому красный **не используется как заливка строки** — только как акцент
  заголовка со значком и словом. Одновременно на экране живут максимум три
  цвета данных: синий план, зелёный факт, янтарный вылет.

### 5.3 Типографика и метрики

- Кегль системного меню (`NSFont.menuFont`, 14 pt на обычных настройках):
  панель висит под строкой меню и читается как её продолжение. Заголовок —
  тот же кегль semibold с трекингом, дни и проценты — обычным начертанием,
  сноски на 2 pt мельче, сводка футера — на 3 pt, вторичным цветом.
- Числа — `monospacedDigit()`, чтобы при обновлении не дёргалась вёрстка.
- Панель: ширина 380 pt, внутренние отступы 14 pt, шаг между строками 10 pt.
  Ширину держит футер: сводка «осталось 42 % · сброс через 3 дн 18 ч · темп
  1.2×» должна вставать в одну строку.
- Тема следует системной (`NSApp.effectiveAppearance`), переключается на лету.
- Форма — как у системных меню строки: своё окно (`NSPanel`, `DropdownPanel`)
  без стрелки-хвостика, верхней кромкой вплотную к строке меню, появление без
  анимации, фон — материал `.menu` с тонкой вуалью поверх (`Theme.panelTint`),
  скругление 12 pt. `NSPopover` не подошёл: стрелку не убрать, отступает от
  строки и рисует свой непрозрачный фон.
- Место панели считается от окна значка, а монитор — по верхней кромке, к
  которой значок ближе всего (`DropdownPanel.screen(for:)`). Спрашивать
  `anchor.screen` нельзя: спрятанная в полноэкранном режиме строка меню уводит
  значок за верхний край своего экрана, а у вплотную стоящих мониторов это уже
  территория соседа — [SPACES.md](SPACES.md), §7.
- Плотность вуали идёт по шкале с потолком `Theme.maxPanelTint` (0.55): на
  полной вуаль гасила материал целиком, и «прозрачный фон с размытием»
  отличался от сплошного одним оттенком. Глухой фон — отдельный режим
  (`transparentPanel`), а не край ползунка.

### 5.4 Строка меню

- Одна картинка ~28×16 pt в два этажа: полоса 3 pt во всю ширину, под ней
  процент 9 pt monospaced. Прежняя раскладка «полоска, рядом текст 12 pt»
  занимала вдвое больше — около 57 pt.
- Цвет по состоянию: в графике — обычный `labelColor`; выше плана — янтарный;
  ≥ 90 % — красный.
- Режим `compact` (только полоска, без числа) — для тех, кто бережёт место.
- Режим `ring` — кольцо диаметром 18 pt, заполняется по часовой от 12 часов,
  число внутри вместо под полосой; в стиле системных значков строки меню
  (заряд, сеть). Дуга и цифра — два разных лимита: настройка `ringArc` решает,
  какой из них на дуге, второй достаётся цифре. Цвета у них раздельные, каждый
  по своим порогам.
- Цифры нарисованы внутри иконки, поэтому за тёмной и светлой строкой меню
  следим сами: KVO на `effectiveAppearance` кнопки перерисовывает картинку.

### 5.5 Состояния

| Состояние | Что видно | Готово |
|---|---|---|
| Загрузка (нет кеша) | приглушённые полосы-плейсхолдеры, «получаю данные…» | да, без шиммера — статичных плейсхолдеров хватило |
| Загрузка (есть кеш) | данные из кеша, кружок источника желтеет на «данные offline» | да, кеш прошлого запуска показывается сразу |
| Оценка (локальный источник) | значок ≈ у процента, подпись «оценка, не официальные данные» | да; подпись стала контурным кружком и его подсказкой |
| Официальный итог | процент без ≈, подпись «разбивка по суткам — оценка» | да, тем же кружком |
| Нет авторизации | «нужна авторизация в Claude Code» | частично: текст есть, кнопки «Как починить» нет — в режиме `auto` вместо неё молча включается локальная оценка |
| Оффлайн | данные из кеша серым + «нет сети, данные от HH:MM» | да, через падение на локальный источник |
| Скоро сброс (< 2 ч) | футер «сброс через 1 ч 12 мин» акцентом | да |
| Лимит исчерпан | заголовок красным, значок ⚠, «лимит недели исчерпан» | да |

Текст ошибки от провайдера панель показывает и сейчас — подсказкой кружка
источника; специализированные подсказки с кнопкой появятся вместе с сетевыми
ошибками.

### 5.6 Доступность

- Каждая строка озвучивается VoiceOver целиком: «Вторник, потрачено 58 процентов
  из 64 плановых, перерасход».
- Значения дублируются числами — цвет никогда не единственный носитель.
- Уважаем «Уменьшение движения»: при включённом — без анимации заливки.
- Режим повышенной контрастности: трек и план берут более тёмные шаги палитры.

## 6. Конфигурация

`~/.config/claude-week/config.json`, читается при старте и по изменению файла:

```jsonc
{
  "resetWeekday": 6,          // 1 = воскресенье … 6 = пятница; запасной путь,
  "resetHour": 16,            //   при живом official момент берётся из ответа
  "resetMinute": 0,
  "timeZone": "Europe/Saratov",
  "refreshInterval": 300,     // секунды, минимум 30; в сеть — не чаще 60 с
  "provider": "auto",         // official | local | auto
  "menuBarStyle": "percent",  // percent | compact | ring
  "weeklyBudget": 0,          // условная стоимость недели для локального режима
  "calibration": { "observedPercent": null, "at": null },
  "thresholds": { "warn": 1.0, "critical": 0.9 }
}
```

`thresholds.warn` — во сколько раз факт может превышать план, прежде чем
пожелтеет цифра в строке меню (1.0 = сразу за плановой отметкой). `critical` —
доля лимита, после которой тревожатся заголовок панели и полоса сессии.
Суточные полосы порогам не подчиняются: янтарный на них — это сам график, а не
тревога.

С тех пор конфиг подрос на раздел `appearance` (тема, прозрачность,
скругление, что показывать). Полная таблица ключей —
[в руководстве](USAGE.md#файл-конфигурации).

## 8. Проверки

Ни XCTest, ни swift-testing без Xcode недоступны (проверено: `swift test` падает
с `no such module 'XCTest'` и `no such module 'Testing'`). Поэтому тесты — это
отдельный исполняемый таргет `ClaudeWeekTests` с минимальным набором
assert-хелперов, запускаемый `swift run ClaudeWeekTests`; ненулевой код возврата
= падение. Когда/если появится Xcode, таргет переносится на swift-testing без
изменения самих проверок.

Что покрыто (477 проверок, `swift run ClaudeWeekTests`):

1. **Окно недели.** Момент ровно на сбросе; за минуту до и после; полсекунды до;
   воскресный полдень; смена таймзоны между вызовами; другой день сброса.
2. **DST.** Недели с переводом часов в обе стороны: 167 и 169 часов, сброс
   остаётся в 15:00 локального времени, сутки перевода длятся 25 часов.
3. **План по рабочим часам.** `planAt(start) == 0`, `planAt(end) == 100`,
   накопительный ряд 10/24/38/53/67/81/96/100 при дне 11:00 → 00:00, ночью
   план стоит, полные сутки весят поровну, круглосуточный режим возвращает
   линейную шкалу. Отдельно — сутки перевода часов: рабочий день остаётся
   правилом циферблата и не съезжает на час.
4. **Парсер jsonl** на фикстурах: строка без `usage`, битый JSON в середине
   файла, кривая дата, `<synthetic>`, дубликат `uuid` в основном файле и в
   `subagents/`, неизвестная модель.
5. **Взвешивание** — известный набор токенов даёт ожидаемую условную стоимость;
   цены и множители кеша сверены отдельно по каждой модели.
6. **Инкрементальный индекс:** неизменившийся файл не перечитывается; дописали
   строку — прочли только хвост и не задвоили записи; файл пересоздали (сменился
   inode) — перечитали целиком; пропавший файл выпал из индекса.
7. **Форматирование** — «3 дн 6 ч», «1 ч 12 мин», проценты без дрожания знаков,
   возраст данных, подписи дней недели.
8. **Конфиг** — частичный файл, комментарии в JSON, битый файл, приведение
   значений к допустимым, запись и чтение.
9. **Метрики футера** — остаток, темп, прогноз, момент исчерпания, пороги
   состояний, поведение сразу после сброса (темп неопределён, а не бесконечен).
10. **Раскладка по суткам и калибровка** — записи прошлой недели не считаются,
    будущие сутки без факта, бюджет по одному наблюдению даёт ожидаемый процент.
11. **Официальный источник** на живом ответе сервера: разбор `seven_day`,
    запасной путь через `limits[kind == "weekly_all"]`, ответ без недельного
    процента даёт ошибку, а не ноль; коды 401/403/429/5xx; отсутствие кред не
    порождает запроса; троттлинг в 60 с; пауза после отказа; окно строится от
    `resets_at`; `provider=local` не ходит в сеть вовсе.
12. **Токен и метки времени** — поиск `accessToken` во вложенной записи,
    миллисекунды и секунды в `expiresAt`, разбор `resets_at` с микросекундами и
    смещением вместо `Z`, кеш прошлой недели признаётся негодным.
13. **Автокалибровка** — официальный процент задаёт бюджет недели; после отказа
    сети локальная оценка даёт то же число и то же окно; момент сброса от
    сервера переживает перезапись кеша локальным снимком и сдвигается целыми
    неделями; без него окно не выдумывается.

Автоматизировано отдельно: `--screenshot` рисует панель в обеих темах в PNG,
не запуская UI; `scripts/probe-usage.swift` снимает живой ответ эндпоинта.

**Ещё не проверено:** VoiceOver, поведение после пробуждения Mac и сутки работы
без утечек — это ручные проверки из критериев M4 и M5, руки до них не дошли.

## 9. Риски

**Р-1. Недокументированный эндпоинт (высокий).** Может измениться без
предупреждения. *Смягчение:* декодер терпимый к незнакомым полям; при ошибке
разбора — не падаем, а переходим на локальный источник с пометкой; схема и дата
проверки зафиксированы в `docs/API.md`.

**Р-2. Доступ к Keychain (средний).** Ad-hoc подпись меняется при пересборке →
повторные системные диалоги. *Смягчение:* «Всегда разрешать» на время разработки;
запасной путь — своя запись Keychain, куда токен кладётся один раз вручную.

**Р-3. Точность локальной оценки (средний).** Веса моделей — приближение
реальной формулы лимита. *Смягчение:* калибровка по одному наблюдению `/usage`;
режим оценки честно помечен в UI.

**Р-4. Объём транскриптов (низкий).** Сейчас холодный проход по 193 файлам —
1.3 с, повторный по индексу — 0.04 с, но архив растёт. *Смягчение:* инкрементальный индекс с самого начала; чтение
только файлов, чей `mtime` попадает в текущее окно.

**Р-5. Сон, смена таймзоны, перезапуск (низкий).** *Смягчение:* подписка на
`NSWorkspace.didWakeNotification` и `NSSystemTimeZoneDidChange`, пересчёт окна
при каждом обновлении, а не один раз при старте.

**Р-6. Отсутствие Xcode (принят).** Закрывает WidgetKit-виджет и штатный
тест-раннер. *Смягчение:* меню-бар с выпадающей панелью вместо виджета
(решение принято и обосновано — приложение Б), свой тест-раннер (§8). Ядро от UI
не зависит, поэтому смена формы подачи не потребует переписывать расчёты.

## 10. Решения по спорным местам

**Время сброса берётся у сервера.** На M3 выяснилось, что он его возвращает
(`seven_day.resets_at`), — как и предполагала оговорка в этом пункте, момент
сброса стал источником истины, а конфиг (`resetWeekday: 6`, `resetHour: 15`) —
запасным значением для офлайна.

Заодно выяснилось, что подтверждённые владельцем «пятница 15:00» расходились с
действительностью на час: сервер сбрасывает в `12:00Z`, то есть в 16:00 по
Саратову. 15:00 — это московское время, а в конфиге стоит саратовская зона.
Пока источником была догадка, все семь полос ехали на час.

**Пятичасовая сессия показывается, но не оценивается.** Второй лимит приходит
в том же ответе (`five_hour`), и панель отдаёт ему первую строку — на практике
упираются чаще в него, чем в неделю. Локально он при этом не считается: веса
моделей приближают недельную формулу, а не сессионную, и второе число по тем же
данным было бы выдумкой. Поэтому офлайн показывается последнее официальное
значение и только пока его `resets_at` в будущем; после сброса строка исчезает,
а из кеша значение стирается. Показать вчерашние 95 % как сегодняшние хуже, чем
не показать ничего.

**Уведомлений нет.** О перерасходе сообщает только цвет: полоса за плановой
отметкой становится янтарной, при исчерпании лимита краснеет заголовок. Ни
баннеров, ни звуков, ни значка на иконке. Если понадобится позже — точка
подключения одна (`Snapshot.state`), но в объём работ это не входит.

**План строки считается на конец суток** — как гласит подпись исходного
скриншота, а не как его цифры (7/21/36/50/64/79/93/100 — это план на середину
суток). Настройка `planAnchor`, позволявшая выбрать между двумя прочтениями,
убрана: факт в строке накопительный и берётся на конец суток, так что план на
их середину систематически рисовал перерасход там, где его не было. Старый
ключ в конфиге игнорируется.

## Приложение Б: почему не виджет Центра уведомлений

Вопрос обсуждался отдельно: показывать данные не в строке меню, а виджетом в
Центре уведомлений — рядом с календарём и погодой. От этого варианта отказались,
и вот на каких основаниях.

**Техническая цепочка.** Виджет — это `.appex`-расширение внутри приложения. Оно
работает в песочнице и не может ни ходить в сеть по своему расписанию, ни читать
произвольные файлы. Данные ему передаёт приложение-контейнер через **App Group** —
общий каталог, объявленный в entitlements обеих частей.

**Где всё упирается:**

1. **App Groups недоступна на бесплатном аккаунте.** Личная команда (Personal
   Team), которую Xcode выдаёт за обычный Apple ID, эту возможность не включает —
   нужна платная подписка Apple Developer Program.
2. **Бесплатный аккаунт ограничен и по сроку:** до 10 идентификаторов приложений,
   каждый живёт 7 дней. Даже обходной путь без App Group упирался бы в
   еженедельную пересборку.
3. **Оплатить $99 в год из России штатно нельзя.** С 1 апреля 2026 обработка
   платежей в App Store в РФ отключена, карты российских банков Apple не
   принимает. Остаются обходные схемы — отдельная возня и постоянные расходы.
4. **Xcode пришлось бы скачать в любом случае** — многогигабайтная установка ради
   того, чтобы упереться в пункт 1.

**Что теряем и что выигрываем.** Виджет живёт на общей панели рядом с погодой —
это его единственное преимущество. Взамен меню-бар даёт:

- обновление тогда, когда нужно нам, а не раз в ~15 минут по решению системы;
- живую панель: наведение, подсказки, кнопки — виджет так не умеет;
- сборку из того, что уже стоит на машине: ни Xcode, ни Apple ID, ни оплаты.

**Визуальный референс** — выпадающая панель приложений вроде Stats или iStat
Menus: иконка в строке меню, клик, панель с графиками. Ровно та форма, что
описана в §1 и §5.

**Если ситуация изменится** (появится платный аккаунт), виджет добавляется
поверх готового ядра: `ClaudeWeekCore` не зависит от UI, и WidgetKit-таргет
станет ещё одним потребителем `UsageSnapshot` наравне с панелью.
