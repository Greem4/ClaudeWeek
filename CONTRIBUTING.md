# Участие в разработке

## Кто ведёт проект

Автор и единственный контрибьютор — [Greem4](https://github.com/Greem4). Все
решения о том, что попадает в код, за ним.

## Как предложить изменение

1. **Заведите issue** и опишите, что не так или чего не хватает. Правка,
   про которую не договорились заранее, может не подойти проекту целиком —
   лучше потратить абзац, чем вечер.
2. **Форк, своя ветка от `main`, pull request.** Прямой push в `main` закрыт.
3. **Один PR — одна мысль.** «Заодно поправил ещё три места» превращает
   разбор правки в археологию.

## Что должно быть зелёным

То же, что гоняет [CI](.github/workflows/ci.yml) — прогоните до отправки:

```bash
# так собирает CI: предупреждение = падение, кроме устаревших объявлений —
# по ним в Keychain.swift есть осознанное исключение, см. комментарий там
swift build -Xswiftc -warnings-as-errors -Xswiftc -Wwarning -Xswiftc DeprecatedDeclaration
swift run ClaudeWeekTests                  # все проверки проходят
./scripts/make-app.sh                      # бандл собирается
```

Меняете расчёты в `ClaudeWeekCore` — добавьте проверку в
`Sources/ClaudeWeekTests`. Ядро специально не знает про UI, чтобы окно недели,
план и проценты гонялись тестами без запуска приложения; ломать это
разделение не надо.

Меняете поведение — поправьте документацию тем же PR:
[README.md](README.md) — витрина, [docs/USAGE.md](docs/USAGE.md) — настройки и
поведение, [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — код и его устройство.
Документация, отставшая от кода, хуже её отсутствия.

## Журнал изменений

Заметное для человека — в [CHANGELOG.md](CHANGELOG.md), в раздел
`## [Не выпущено]`, тем же PR, что и сама правка. Журнал по-русски, как и всё
остальное в проекте: его читают те же люди, что README, — и в программе, и на
странице выпуска.

Разделы — русские заголовки Keep a Changelog: `Добавлено`, `Изменено`,
`Исправлено`, `Убрано`, а ещё `Заметки` — для оговорок, которые сами по себе не
изменение, но знать о них надо. Строка пишется про поведение, а не про код:
«щелчок по проценту открывает разбивку по моделям», а не «добавил
ModelsWindowController». Внутренняя правка, о которой человеку знать нечего,
сюда не идёт вовсе — для неё есть история git.

Заголовок «Не выпущено» превращается в номер версии сам:
[`release-on-merge.yml`](.github/workflows/release-on-merge.yml) закрывает
раздел тем же шагом, которым поднимает версию, и заводит сверху новый пустой.
Руками этого делать не нужно, и помнить об этом тоже: пока помнить было надо,
записи 0.1.10 уехали в релиз, оставшись под заголовком «не выпущено».

Дальше закрытый раздел уходит в заметки к релизу — их собирает
[`release.yml`](.github/workflows/release.yml), и написанное вами видит каждый,
кто откроет страницу выпуска; список коммитов остаётся там же, свёрнутым.
Раздел пуст — заметки соберутся из сообщений коммитов, как раньше.

Что уедет в релиз, видно заранее:

```bash
./scripts/changelog.sh section 0.1.11              # текст будущих заметок
./scripts/changelog.sh release 0.1.11 --dry-run    # как закроется раздел
```

## Коммиты

- одна строка, до 72 символов, без тела;
- по-русски, глагол в прошедшем времени: «Добавил», «Исправил», «Убрал»;
- одна главная мысль, без перечисления файлов и классов;
- без префиксов `feat:`, `fix:`, `chore:`.

Например: `Добавил уведомление о перерасходе недельного лимита`.

## Как выходит релиз

Ничего делать не нужно: слили PR в `main` — версия поднялась, тег встал, образ
собрался и уехал в Releases. Этим занимается
[`release-on-merge.yml`](.github/workflows/release-on-merge.yml), сборкой —
[`release.yml`](.github/workflows/release.yml).

Разряд версии выбирается меткой на PR **до слияния**:

| Метка          | Что будет     |
|----------------|---------------|
| нет метки      | патч: 0.1.6 → 0.1.7 |
| `версия:минор` | 0.1.6 → 0.2.0 |
| `версия:мажор` | 0.1.6 → 1.0.0 |
| `без-релиза`   | версия и релиз не трогаются |

Релиз не выйдет и без метки `без-релиза`, если PR не тронул ничего, кроме
`*.md` и `docs/`: выпускать сборку ради правки текста незачем.

Разряд считает до 99 и переносится в старший: 0.1.99 → 0.2.0, 0.99.0 → 1.0.0.
Двузначные числа законны — 0.1.10 идёт после 0.1.9, а не наоборот.

Версию в `Sources/ClaudeWeekCore/Version.swift` руками поднимать не надо —
подняли в самом PR, workflow это увидит и выпустит ровно ту цифру, что в файле,
а не следующую. Видит он это по тегу: номер в файле ещё не выпущен — значит его
и берём. Правка соседних строк того же файла на разряд не влияет — раньше
влияла, и релиз локализации встал на уже занятом теге. После слияния сделайте
`git pull`: в `main` уехал коммит бота — с новой версией и закрытым разделом
журнала.

Посчитать версию локально — тем же скриптом, которым это делает workflow:

```bash
./scripts/bump-version.sh minor --dry-run   # покажет 0.2.0 и ничего не запишет
```

Если релиз всё-таки нужно выпустить руками (событие потерялось, сборка упала) —
это обычный тег: `git tag v0.2.0 && git push origin v0.2.0`, либо Actions →
Release → Run workflow с готовым тегом в поле `ref`. Раздел журнала при таком
выпуске никто не закроет, поэтому закройте его сами — до тега:

```bash
./scripts/changelog.sh release 0.2.0
```

Забыли — релиз не пострадает: заметки соберутся из раздела «Не выпущено», как
он есть. Но в журнале версия так и останется незакрытой, а это ровно та
забывчивость, из-за которой записи 0.1.10 однажды уехали в релиз безымянными.

## Стиль кода

Swift 6 со строгой изоляцией. Смотрите на соседний код и пишите так же:
комментарии по-русски и о том, **почему** так сделано, а не что делает
строка. Грабли, на которые уже наступали (изоляция акторов, признаки рабочего
стола, арифметика с часами), собраны в разделе «Грабли»
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Правите панель
(`DropdownPanel`) — сначала [docs/SPACES.md](docs/SPACES.md): там измерения и
пробы, без которых это место чинится наугад.
